How MCP works

A user's request flows through an agent, out to a tool server, and back — five stages, every one of them a hop of trust.

Tool results flow back the same path, right to left

Now let's place that tool loop inside the full system. This is the architecture of any MCP-based agent, and it has five stages. On the far left is the user, who types an ordinary request, for example "get me the current working directory." Next is the LLM agent. This is the language model plus a small amount of code that runs the think, act, observe loop we just saw. It reads the request, reads the descriptions of the tools available, and decides which tool to call and with what arguments. The MCP client is the plumbing on the agent's side. It turns the agent's decision into a protocol message and routes it to the right server. Think of it as the agent's network card for tools. The MCP server is a separate program that hosts one or more tools. It might be written by the same team, or downloaded from a third party. Crucially, it is the server that tells the agent what its tools are called and what they do. Finally, the tools themselves: the code that actually touches files, APIs or the shell. The request flows left to right, and the tool's reply flows all the way back right to left, into the agent's context. Every arrow on this slide is a hop where one component trusts the text it receives from the next. On the next slide, we'll mark the four hops an attacker targets.
