Conclusion

What this project actually shows

MCP-SecBench is a prototype middleware defense against selected MCP attack classes, integrated with the MSB benchmark so that undefended and defended agents can be compared under identical conditions.

We showed

A proxy can be attached to MSB's agent without changing MSB. All 12 attack types execute. On the parameter attack, leaks fell to 0% on both models — from 100% on the 8B model — with every attempt blocked by the guard.

We did not show

General MCP security, defense against reworded or unseen attacks, protection from MSB's prompt injection, or anything about the cost to legitimate tasks.

We learned

Check that the agent really used its tools, and that your judge measures what the attack does. Both mistakes were in our first draft — and fixing them turned "0%" into "100% → 0%."

Let's close by being precise about what this project actually shows. The box at the top is the claim, and I've chosen the words carefully: MCP-SecBench is a prototype middleware defense against selected MCP attack classes, integrated with the MSB benchmark so undefended and defended agents can be compared under identical conditions. Not "a solution to MCP security." Not "detects prompt injection." A prototype, against selected classes, measured under controlled conditions. What we showed. First, that a defensive layer can be attached to MSB's agent from the outside, without editing MSB, which is what makes the comparison trustworthy. Second, that all twelve of MSB's attack types execute in this setup. Third, a measured effect on the out-of-scope parameter attack, on both models. With the native prompt, the eight-billion model leaked in all twenty-five undefended scenarios and in none of the twenty-five defended ones; the three-billion model went from twenty-four or thirty-six percent, depending on the prompt setting, to zero. In every defended scenario where a model attempted the leak, the guard was the reason it failed. What we did not show. We didn't show general MCP security. We didn't show the guard holds up against attacks that are reworded or that it has never seen, and given that it matches fixed patterns, we expect it often wouldn't. It doesn't protect against MSB's prompt injection at all. And we haven't measured what it costs legitimate tasks. And the third card is the lesson I'd most like you to take away, because it applies to any security evaluation, not just this one. Two mistakes in our first draft nearly led us to the wrong conclusions. One: we didn't check whether the agent was actually executing tools, so we read "zero percent" as "resisted" when often the attack never arrived. Two: our judge for parameter attacks was looking for a file that attack never creates, which hid the effect entirely. Fixing both turned a meaningless "zero percent" for the larger model into "one hundred percent, down to zero." Verifying the measurement is as important as building the defense. Thank you.
