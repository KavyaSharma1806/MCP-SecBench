This is the full map of MSB's twelve attack types against our implementation, with three questions for each. Executable: does a scenario of this type run end to end in our setup? All twelve do. We verified the nine we hadn't run statistically with one scenario each, undefended and defended, and none crashed. Scored: does our judge give a meaningful verdict? Eleven yes. The asterisks mark the three parameter-leak types, whose judge we fixed in this version to match MSB's definition. Retrieval injection is the exception, because MSB doesn't score it as attack success at all and we have no valid judge yet. Defended: does our guard actually address this attack's mechanism? We decided this by reading each attack's real source code and checking it against the guard's intervention counts, not by assuming. And the rule is strict: "Yes" only if every part of the attack is addressed. Four are a clean yes. False error and simulated user, because their replies carry text the response sanitizer recognizes. Out-of-scope parameter, through the parameter gate, which is where our one measured reduction comes from. And tool transfer, whose fake "this tool is no longer available" reply starts with IMPORTANT in angle brackets, plus a parameter-gated follow-up. Seven are partial. Name overlap and preference manipulation use near-miss tool names like execute_command_v1, which our exact-match check misses, though the decoy's reply is still caught once it's called. Retrieval injection is caught in two of MSB's four documents, the two that wrap the instruction in IMPORTANT. And the four combined attacks are partial because one of their two halves isn't covered. And one is a flat no, the red row: prompt injection. When we first built this table we marked it defended, and that was wrong. MSB doesn't place the injection inside any tool's description field. It appends it to the system prompt text directly. Our signature validator only scans description fields, so it never sees it, and when the guard rebuilds the system prompt, MSB's own code appends the injection again. The intervention count confirms it: zero, across fifty defended runs. All the defended agent gets is our policy text telling it not to follow instructions from tool content. That's a real gap, and per our project plan we're documenting it rather than quietly patching it.
