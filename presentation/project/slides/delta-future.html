Proposed delta: what comes next

NEAR TERM

Close the gaps we found

Prompt-injection coverage

Scan the full system prompt, not only tool descriptions

Fuzzy tool-name matching

Catch near-miss names like execute_command_v1

Usefulness metrics

PUA, NRP and false positives on benign tasks

NEXT

Smarter detection

Semantic detector

Classify tool text as data or instruction, robust to rewording

Permission policies

Ask whether an action is allowed for this request

Sequence monitoring

Flag risky chains, e.g. read a secret, then write a file

LONGER TERM

Prove it generalizes

Unseen-attack tests

Renamed fields, paraphrased payloads, new tools

Full MSB grid

All 12 types, more and larger models, MSB's 10 steps

Retrieval-injection judge

A valid oracle so it can finally be scored

And this is the delta we propose next, ordered from the smallest step to the most ambitious. To be clear, none of this is done yet. It's the plan. Near term, close the gaps we found ourselves. Scan the full system prompt so MSB's prompt injection is covered. Match near-miss tool names instead of exact duplicates. And measure usefulness: task completion and false positives on benign tasks, so we know what the guard costs. Next, smarter detection. A semantic detector that judges what text means rather than matching keywords. Permission policies that ask whether an action is allowed for this request, not just whether it looks malicious. And monitoring of risky action sequences, like reading a secret and then writing it to a file. Longer term, prove it generalizes. Test on attacks the guard has never seen: renamed fields, paraphrased payloads, new tools. Run the full MSB grid on more and larger models with MSB's ten steps. And build a valid judge for retrieval injection so it can finally be scored.
