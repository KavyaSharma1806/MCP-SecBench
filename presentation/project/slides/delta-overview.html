Rule we followed: if MSB already does it, it is not our contribution — even if we re-implemented it.

This is the slide that answers "so what did you actually do?" And I want to be strict about it: if MSB already does something, it is not our contribution, even if we wrote our own version of it. The first row is what we did not change. MSB's attacks, its five goals, its ten personas and its malicious servers are the benchmark. We used them untouched. The baseline folder in our repository is MSB's code, unedited, apart from redacting some API keys its authors had accidentally committed. Everything in green is new. Defense: MSB's repository contains no defensive code at all. It measures how often attacks work. We built mcp_guard, a middleware layer with three components plus a security policy added to the system prompt. Most of the remaining slides are about how it works. Experiment design: because MSB has no defense, it only ever runs undefended agents. We run every scenario twice, once without the guard and once with it, holding everything else identical: same model, same task, same attack, same servers. That pairing is what turns a measurement into a comparison. Metrics: MSB's three metrics measure an attack. A defense needs different questions answered, so we added mitigation rate, guard interventions per component, and we record the agent's actual tool calls for every scenario, so anyone can audit why a scenario was scored the way it was. Judging: MSB writes logs during the run and parses that text afterwards with pattern matching. We judge in-process, directly from the sandbox files and from the live trajectory of tool calls. That's simpler, it doesn't break if a log format changes, and as you saw on the previous slide, our file checks are stricter about content. Models: MSB is wired to hosted APIs that need keys. We added local models through Ollama, so this entire study costs nothing and runs offline, which is how every number in this deck was produced. Platform: MSB's setup script assumes Linux or macOS and moves a file in a way that would delete it from the benchmark folder. Ours runs on Windows and keeps the benchmark intact. And audit: we checked that all twelve attack types actually execute, we read each attack's source code to see what our guard really catches, and in doing so we found gaps in our own guard and a bug in our own judge. All of that is documented, not hidden. Last row, validity. MSB never checks whether the agent actually executed its tools in each scenario, and it turns out that matters enormously: under MSB's exact prompt, our eight-billion model almost never did. We measure it, and we added a second prompt setting that removes the one instruction causing the problem, reported side by side with MSB's.
