mcp_guard.py

Three components, one proxy

SecurityGuard

apply_defense(agent)

Tool Signature Validation

Drops exact duplicate tool names. Strips known injection markers out of each tool's description field.

catches: <INFORMATION>, <IMPORTANT>, exact duplicates

misses: near-miss names, MSB's prompt injection

Parameter Gating

Refuses tool calls carrying out-of-scope keys, secret-like keys, or high-risk payloads before dispatch.

catches: llm_model_name, api_key, ssh-rsa content

Response Sanitization

Scans tool observations for MSB's canned attack templates and redacts them before the LLM reads them.

catches: fake "Error", fake "new user query"

Let's zoom into the guard. The green box from the previous slide has grown, and you can see it has three components, one for each attack surface that is reachable at this point in the pipeline. Left: tool signature validation. This runs once, when the agent is set up. It looks at the list of tools the servers advertised. If two tools have exactly the same name, it keeps the first and drops the duplicate. And it scans every description for phrases that are known injection patterns, like the information-block wrapper or the word IMPORTANT in angle brackets, and strips them out before the description ever reaches the model's system prompt. We found two real gaps here, shown in the red line. First, it only catches exact duplicate names, and MSB's real name-collision attacks use near-miss names like an extra "v1" on the end. Second, and more surprising: it does nothing against MSB's prompt injection attack. MSB doesn't put that injection inside any tool's description field; it appends it to the system prompt text itself, and this component only scans description fields. We confirmed it from the intervention counts: zero, in fifty defended runs. Middle: parameter gating. This runs before every single tool call. It looks at the arguments the agent wants to send. It refuses calls that carry MSB's out-of-scope field, llm_model_name; calls that carry anything shaped like a secret, an API key or a password; and calls to dangerous tools like write_file whose payload contains an SSH key or references the personal data file. Right: response sanitization. This runs after every tool call, on whatever came back. It scans for known attack phrasing, MSB's fake error message, the fake new-user message, and generic "ignore previous instructions" style text, and if it finds any, the reply is withheld and replaced with an explanation. There's also a fourth, quieter piece not shown as a box: a security policy appended to the system prompt, telling the model that tool output is data, not instructions. One more thing to notice in the small grey text: everything here is pattern matching against known phrases. That makes it fast and transparent, and it also makes it beatable by an attacker who simply words things differently. We'll come back to that.
