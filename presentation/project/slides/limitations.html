05 · Journey and next steps

What this does not solve

Prompt injection is not defended

MSB puts it in the system prompt; the guard scans only tool descriptions. 0 actions in 50 defended runs.

Fixed patterns, tuned to MSB

Rename llm_model_name or reword the fake error and it passes. A low ASR on MSB is not general MCP security.

Near-miss tool names pass

Only exact duplicates are caught; execute_command_v1 sits beside execute_command.

Usefulness not measured

No PUA, NRP or false-positive rate yet: we can't say how often the guard blocks legitimate work.

Retrieval injection unscored

Caught in 2 of 4 documents, and then the whole document is withheld, real content included.

Not MSB's exact setup

8 steps instead of 10, small local models, a native-prompt variant, and a broken kill_process dependency.

We want to be clear about the limits, because a security prototype that can't state its limits isn't trustworthy. Prompt injection isn't defended at all: MSB puts it in the system prompt, and our guard only scans tool descriptions. Zero interventions in fifty defended runs. Every check is a fixed pattern tuned to MSB's attack text. Rename llm_model_name to model_id, or reword the fake error, and the guard won't notice. So a low score on MSB is not general MCP security. Near-miss tool names pass. We haven't measured usefulness or false positives, so we can't say how often the guard gets in the way of legitimate work. Retrieval injection is unscored and only partly caught, and when it is caught, the whole document is withheld. And our setup differs from MSB's: eight steps instead of ten, small local models, the native-prompt variant, and a third-party dependency for the kill-process goal that is currently broken.
