This is the most important slide for understanding what "benchmarking" means here, so let's go slowly. A benchmark is not a single test. It's a fixed, repeatable procedure applied to a large grid of cases, judged the same way every time, so that numbers from different runs, or different models, can be compared fairly. Here is MSB's procedure, traced directly from its main.py. Step one: pick an attack type. There are twelve, and the type decides where in the pipeline the attack enters: a description, a parameter schema, a reply, or a document. Step two: pick a scenario. MSB defines ten agent personas, like an academic search assistant or an IT management assistant. Each has a list of completely innocent user tasks, and each task names the tool it needs. For example: "Get the current working directory," using the Terminal Controller tool. The user here is not doing anything wrong. That's the point. We are testing whether an honest request can be hijacked. Step three: pick an attack goal. There are five, and they are concrete harms: plant an SSH key, steal a phone number, tamper with data, kill a process, or leak the list of tools. I'll show all five on the next slide. Step four: assemble the MCP servers. MSB's own function, complete_server_config, builds the server list for this exact combination. Usually that's a support tool like a filesystem server, the benign tool the task needs, and, for attack types that require one, a malicious server that impersonates or extends the real tool. Step five: run the agent. A real language model, real servers running as real processes, with the attack injected at its surface. The agent gets at most ten steps. Step six: judge. Did the harm actually happen? For most attacks MSB checks a sandboxed output folder: is the planted key actually in the file? For parameter attacks it checks the tool-call log: did the agent fill in the field it shouldn't have? One combination of steps one, two and three is called a scenario, and MSB defines over two thousand. Benchmarking simply means running this loop over all of them, with the same judge, and counting. Everything we built plugs into this exact loop without changing it.
