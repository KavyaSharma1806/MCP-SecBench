This slide is about a finding that changed how we read our own results, and I think it's one of the most useful things in this project. Here is the question nobody had asked: in each scenario, did the agent actually use its tools? It sounds obvious, but it matters enormously. Every attack in MSB arrives through the tool loop: through a tool description, a tool's schema, a tool's reply, or a document a tool fetched. If the agent never actually executes a tool call, the attack has nothing to ride on. It can't succeed, and the guard has nothing to block. What we found is a mismatch inside the setup MSB uses. MSB's system prompt, the instructions given to the model, describes an old text-based protocol: write "Thought," then "Action," then "Action Input." But the agent framework underneath expects native tool calls, a structured format the model returns separately from its text. MSB's published numbers show non-zero attack success for hosted versions of these models, which implies their tool calls did execute there; we can't verify how. Our local models frequently didn't execute. They followed the text instructions literally: they wrote out the tool call as text, as their final answer, and stopped. The framework saw a final answer, not a tool call, so nothing was executed. The box in the middle is a real example from the eight-billion-parameter model. It wrote "Action: search_query" and an action input, and look, it even filled in llm_model_name with "My AI Model." If that had been a real call, it would have been a leak. But it was just text on the screen. No server received it, and our judge correctly scored no leak. The numbers on the right count how often a scenario ended this way. For the eight-billion model, sixty-five out of seventy-five baseline scenarios. For the three-billion model, forty-one out of seventy-five. This indicator only looks at the final answer, so it isn't a perfect count of runs where no tool ever executed, but it tells you this is not a rare edge case. What this means, plainly. In an earlier draft we said that zero percent attack success on prompt injection and false error showed the models resisting these attacks, and that the larger model ruled out model size as an explanation. That claim isn't supported, and we've withdrawn it. For the eight-billion model especially, the attack mostly never reached it: in the parameter-leak scenarios, where we record every executed call, it made zero real tool calls in twenty-five baseline runs. The three-billion model is more mixed. False-error attacks did reach it often, since the guard redacted them twenty-seven times in defended runs, yet in the baseline it never completed the harmful file write. What survives is on the green card: the parameter-leak results. Since fixing our judge, we record every tool call that actually executed, and a leak is only counted when a real call reached a server. Those numbers are measured on real behavior. We deliberately did not rewrite MSB's prompt to "fix" this, because then our baseline would no longer be MSB's baseline. Instead we report it, and it's at the top of our list of things to measure properly next.
